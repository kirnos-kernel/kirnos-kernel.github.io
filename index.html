# Architectural Specification & Design Document: **KirnOS** **Next-Generation Unified Operating System** *Engineered from the ground up in the Kirn Systems Programming Language* --- ## 1. Executive Vision & Core Philosophy Current operating systems carry decades of historical baggage: * **Windows (NT)** features an exceptional object manager, asynchronous I/O (IOCP), and unmatched backward compatibility, but suffers from registry corruption, legacy Win32 bloat, fragmented configuration, and forced reboots. * **Linux** offers unbeatable modularity, high-throughput container primitives (`cgroups`, `namespaces`), and modern asynchronous I/O (`io_uring`), but suffers from desktop fragmentation, unstable kernel ABIs for out-of-tree drivers, and messy user-space packaging. * **macOS (Darwin/XNU)** provides world-class audio/visual low-latency pipelines (CoreAudio, Metal), elegant application bundles (`.app`), and robust sandboxing, but remains walled off, proprietary, and historically burdened by a heavy hybrid Mach/BSD kernel. * **Unix / FreeBSD / Plan 9 / BeOS**: FreeBSD brings rock-solid ZFS storage pools and Capsicum capability sandboxing; Plan 9 pioneered pervasive synthetic filesystems and per-process namespaces; BeOS demonstrated the power of a fully multithreaded, database-indexed filesystem (BFS). **KirnOS** synthesizes these pinnacle innovations into a unified, zero-debt architecture written in **Kirn**—a modern systems programming language that pairs deterministic memory control, zero-cost abstractions, compile-time metaprogramming, and formal memory safety. ``` +-----------------------------------------------------------------------------------+ | KirnOS Application Layer | | +--------------------+ +--------------------+ The Kirn Language Integration Kirn serves as the sole implementation language for KirnOS, fulfilling low-level bare-metal demands while retaining high-level ergonomics: 1. **Dual-Mode Memory Governance**: * **`safe` mode**: Employs linear types and ownership borrow semantics (similar to Rust), mathematically preventing data races, use-after-free, and dangling pointers at compile time. * **`bare` / `@unsafe` blocks**: Grants direct pointer arithmetic, volatile register reads/writes, memory-mapped I/O (MMIO), and inline assembly for page tables and context switches. 2. **Compile-Time Metaprogramming (`comptime`)**: * Hardware device structs, register bitfields, and system call tables are validated and optimized during compilation, eliminating runtime reflection overhead. 3. **Zero Runtime & No Garbage Collector**: * Kirn has no hidden tracing garbage collector or mandatory runtime thread manager. Memory allocation uses pluggable regional arena allocators (`RegionAlloc`), slab allocators, and deterministic physical frame banks. 4. **First-Class Error Handling**: * Result unions (`Result[T, KernelError]`) enforce complete and exhaustive kernel error handling. Errors cannot be silently ignored. --- ## 4. Kernel Architecture: KirnCore KirnCore is an ultra-fast **Micro-Hybrid Kernel**: ### 4.1. Lockless Asynchronous Syscall Engine (`KirnRing`) Syscalls in KirnOS bypass legacy high-overhead software interrupts (`sysenter`/`syscall`) for high-throughput batching. Processes map a shared memory page containing two lock-free ring buffers: 1. **SQ (Submission Queue)**: User space pushes operations (read, write, allocate, IPC send). 2. **CQ (Completion Queue)**: Kernel space posts completion statuses. System call overhead drops to zero CPU cycles per operation under heavy load, as work batches without context switches. ### 4.2. Object Manager & Capability Handle System Following Windows NT and seL4: * Resources are created as `KernelObject` instances. * Processes receive opaque `Handle` pointers indexable only through the process's private Capability Table. * Each `Handle` carries immutable permission masks (e.g., `READ | SEEK`, but not `WRITE`). * Ambient authority is prohibited: a process cannot access a path `/etc/config` unless passed an explicit handle to that namespace node. --- ## 5. KirnFS: The Unified Storage Engine KirnFS combines **ZFS reliability**, **BeOS searchable metadata**, and **Apple APFS space-sharing**: 1. **Copy-on-Write (CoW) B-Trees**: * Modifying blocks never overwrites existing disk sectors. New blocks are written to unallocated space, and parent pointers update atomically via single-transaction commits. 2. **End-to-End Cryptographic Checksumming**: * Every sector is hashed with BLAKE3. Silent data corruption (bit rot) is detected on read and automatically repaired using parity mirrors. 3. **Database-Indexed Metadata Engine**: * Attributes like `author`, `bitrate`, `dimensions`, or `git.branch` are first-class indexed attributes stored in local B-Trees. * Query: `find . where audio.sample_rate >= 96000 and audio.format == "flac"` returns in sub-millisecond time across millions of files. 4. **Instant Atomic Snapshots & Time-Shift Rolling**: * System updates occur in an isolated snapshot. If an update fails, the bootloader rolls back the root filesystem block pointer instantly. --- ## 6. The User Space & Application Framework ``` +--------------------------------------------------------------+ | KirnOS App Ecosystem | +------------------------------+-------------------------------+ | Native Kirn Applications | Compatibility Subsystems | | - .kapp Multi-Arch Bundles | - Kirn-Linux (Syscall Trans.) | | - KirnSurface Vector Engine | - Kirn-WinNT (DLL & PE Emul.) | | - Grand Task Dispatch (GTD) | - Native POSIX.1-2024 Runtime | +------------------------------+-------------------------------+ ``` ### 6.1. The `.kapp` Application Bundle Taking the best of macOS: * Applications are distributed as unified directories: ```text Photos.kapp/ ├── Manifest.kirn # Declarative sandbox rules & permissions ├── Binary/ │ ├── x86_64.elf │ └── aarch64.elf ├── Resources/ # Icons, localizations, assets ├── Interfaces/ # Exposed IPC endpoints (Plan 9 synthetic nodes) └── Signatures/ # Cryptographic developer signature & integrity hash ``` * No shared dependency conflicts; each app bundles its specific private libraries or targets pinned system ABI contracts. ### 6.2. Grand Task Dispatch (GTD) Drawing from Apple’s Grand Central Dispatch and Windows thread pooling: * Developers do not manage raw OS threads directly. * Developers dispatch lightweight closures or fibers to priority queues: `Queue.high_priority`, `Queue.audio_realtime`, `Queue.background`. * The kernel dynamically schedules fibers onto physical CPU cores utilizing lockless work-stealing queues. ### 6.3. Triple-Layer Compatibility Engine To eliminate the classic "new OS app desert": 1. **POSIX Layer**: Built-in, fully conforming POSIX.1-2024 C runtime (`libkirn_posix`), allowing compilation of Git, Curl, Python, LLVM, and core utilities out of the box. 2. **KirnLinux Personality**: In-kernel syscall translation engine mapping Linux system calls (`clone`, `epoll`, `prctl`) to `KirnRing` equivalents, running standard dynamic ELF binaries directly. 3. **KirnWin Subsystem**: Built-in user-mode Win32/NT executive runtime translating Direct3D 12 calls to KirnSurface/Vulkan, and Win32 handles to KirnCore handles. --- ## 7. Graphics & Compositor: KirnSurface Abandoning both the historic network latency of X11 and the missing shared standards of early Wayland, **KirnSurface** provides: * **Direct Hardware Scanout & Zero-Copy Compositing**: The display compositor shares unified memory buffers with GPU hardware queues. * **Declarative Retained-Mode UI Stack**: System UI is written in Kirn’s declarative vector layout framework, compiled directly to GPU shader pipelines. * **Tearing-Free Variable Refresh Rate (VRR)**: Every display buffer is synchronized via explicit GPU timelines. --- ## 8. Kirn Source Code Implementations Below are concrete, production-style source code samples showcasing how KirnOS is implemented in the **Kirn programming language**. ### 8.1. The Kernel Ring Buffer & Handle Structure (`kernel/ring.kn`) ```kirn module kernel.core.ring; import kernel.arch.x86_64.cpu; import kernel.memory.address; import kernel.security.capability; pub enum OpCode : u16 { NoOp = 0x00, Read = 0x01, Write = 0x02, AllocPages = 0x03, FreePages = 0x04, ChannelSend = 0x05, ChannelRecv = 0x06, CreateEvent = 0x07, } pub struct RingEntry { pub opcode: OpCode, pub flags: u16, pub handle_id: u32, pub buffer_ptr: PhysAddr, pub length: u64, pub user_data: u64, } pub struct CompletionEntry { pub user_data: u64, pub result: i64, pub flags: u32, } pub struct KirnRing[const QUEUE_SIZE: usize] { submission_head: atomic[u32], submission_tail: atomic[u32], completion_head: atomic[u32], completion_tail: atomic[u32], submissions: [RingEntry; QUEUE_SIZE], completions: [CompletionEntry; QUEUE_SIZE], pub fn init() -> Self { return Self { submission_head: atomic.new(0), submission_tail: atomic.new(0), completion_head: atomic.new(0), completion_tail: atomic.new(0), submissions: [RingEntry::default(); QUEUE_SIZE], completions: [CompletionEntry::default(); QUEUE_SIZE], }; } pub fn process_submissions(&mut self, cap_table: &CapabilityTable) -> u32 { let mut processed: u32 = 0; let head = self.submission_head.load(Ordering::Acquire); let tail = self.submission_tail.load(Ordering::Relaxed); while head != tail { let index = (head % QUEUE_SIZE as u32) as usize; let entry = self.submissions[index]; // Verify caller capability before executing operation let status = match cap_table.verify(entry.handle_id, entry.opcode) { Result::Ok(cap) => self.dispatch_op(&entry, cap), Result::Err(err) => err.as_raw_code(), }; self.push_completion(entry.user_data, status); self.submission_head.store(head + 1, Ordering::Release); processed += 1; } return processed; } fn push_completion(&mut self, user_data: u64, status: i64) { let tail = self.completion_tail.load(Ordering::Relaxed); let index = (tail % QUEUE_SIZE as u32) as usize; self.completions[index] = CompletionEntry { user_data: user_data, result: status, flags: 0, }; self.completion_tail.store(tail + 1, Ordering::Release); } @inline(always) fn dispatch_op(&mut self, entry: &RingEntry, cap: ValidCapability) -> i64 { // Dispatch to zero-copy memory or channel pipeline return 0; // Success } } ``` --- ### 8.2. KirnFS: High-Integrity CoW Block Allocator (`fs/kirnfs.kn`) ```kirn module fs.kirnfs.allocator; import crypto.blake3; import storage.nvme; import kernel.memory.alloc; pub struct BlockAddress(pub u64); pub struct MerkleNode { pub logical_id: u64, pub physical_lba: BlockAddress, pub generation: u64, pub block_size: u32, pub checksum: [u8; 32], // 256-bit BLAKE3 hash } pub struct KirnFSRoot { pub transaction_id: u64, pub root_tree_lba: BlockAddress, pub global_checksum: [u8; 32], pub fn write_block_cow( &mut self, node: &MerkleNode, data: []const u8 ) -> Result[MerkleNode, StorageError] { // 1. Verify buffer length matches block boundary if data.len() != node.block_size as usize { return Result::Err(StorageError::InvalidBlockSize); } // 2. Compute BLAKE3 cryptographic integrity checksum let computed_hash = blake3::hash(data); // 3. Allocate fresh sector (Copy-on-Write: Never overwrite old block) let new_lba = nvme::allocate_free_block()?; // 4. Commit write to new storage address nvme::write_dma(new_lba, data)?; // 5. Construct updated Merkle node for atomic root swap let updated_node = MerkleNode { logical_id: node.logical_id, physical_lba: new_lba, generation: node.generation + 1, block_size: node.block_size, checksum: computed_hash, }; return Result::Ok(updated_node); } } ``` --- ### 8.3. Hardware Support & Portability Strategy KirnOS utilizes a modular **Hardware Abstraction Layer (HAL)** written in Kirn: * **x86_64**: Bootstraps via 64-bit UEFI, initializes APIC/IOAPIC, enables 4-level/5-level paging, and leverages AMD-V / Intel VT-x hardware virtualization for subsystem translation. * **AArch64**: Utilizes standard Device Trees (FDT) and ACPI, targeting Apple Silicon, Snapdragon X Elite, and Raspberry Pi 5. Configured with 4KB/16KB/64KB pages and TrustZone/EL2 hypervisor primitives. * **RISC-V (RV64GC)**: Direct integration with Sv39/Sv48/Sv57 MMU paging, SBI (Supervisor Binary Interface), and the standard vector extensions for cryptographic operations. --- ## 10. Summary & Roadmap KirnOS achieves an optimal operating environment by unifying historical breakthroughs while eliminating legacy deadweight: * It matches **Windows** in handle security and non-blocking asynchronous throughput. * It matches **macOS** in desktop polish, bundle portability, and real-time audio latency. * It matches **Linux** in container agility, zero-overhead ring syscalls, and developer flexibility. * It leverages **FreeBSD & BeOS** in self-repairing storage and live database queries. Written natively in **Kirn**, the entire operating system achieves memory safety without garbage-collection interruptions, yielding a predictable, secure, and modern operating system.
